# Жизненный цикл задачи и вопросы воркера

Машина статусов закодирована в `packages/protocol/src/status.ts` (`TRANSITIONS`); менеджер сессий отклоняет любые другие переходы.

```
queued ─► planning ─► needs_input ─► planning/running
   │         │              ▲
   │         ▼              │ ask (критичный)
   └──────► running ────────┘
              │ agent_settled
              ▼
           checking ─► done
              │  └──► failed ─(2 FAIL подряд)─► новая задача на следующей модели (escalated_from_task_id)
              └──► running (возврат через send с замечаниями)

любой активный ─► cancelled (cancel, worktree сохраняется)
running/planning/checking ─► interrupted (рестарт хаба) ─► running (switch_session)
активный без владельца > orphan_after_minutes ─► orphaned ─► adopt
```

## Доставка вопроса

1. Воркер вызывает инструмент `ask(question, options?)` из расширения pi-hub.
2. Расширение делает `ctx.ui.select` (есть варианты) или `ctx.ui.input`. В RPC-режиме Pi пишет в stdout `extension_ui_request {id, method, title, options}` и **ждёт** — токены не тратятся.
3. RPC-клиент хаба сохраняет вопрос в `questions` (`round`, `options_json`).
4. System One (`critical?`) решает адресата:
   - некритичный → консультант (более сильная дешёвая модель + спецификация задачи), ответ возвращается сразу;
   - критичный → статус `needs_input`.
5. Старшему вопрос доходит тремя путями: завершается его `wait`; подвал любого ответа хаба («ожидают ответа: t_0142, 1 вопрос»); хук `Stop` блокирует завершение хода с текстом вопроса.
6. `send(task_id, message)` → `extension_ui_response {id, value}` → расширение возвращает ответ воркеру.
7. Если старший молчит дольше `notify_user_after_minutes` → уведомление пользователю.

Фаза вопросов до работы (`clarify`) — тот же механизм: первый промпт просит прочитать код и вернуть план и вопросы через `ask`, до ответа писать код нельзя.

**Нарушение протокола** (воркер задаёт вопрос текстом в ответе вместо `ask`, или правит файлы в фазе `planning`): задача отменяется и перезапускается; исходная задача и история ответов идут в новый промпт обычным текстом.

## `wait` и таймауты клиентов

`wait(task_id, timeout)` — длинный опрос. Хаб обрезает `timeout` до `min(запрошенный, client_tool_timeout − запас)` и возвращает текущий статус, если ничего не произошло. Таймаут клиента берётся из конфига плагина (Codex: `tool_timeout_sec`). См. ADR-0006.

## Перезапуск хаба

При старте: все задачи в `running|planning|checking` с мёртвым `pid` → `interrupted`. Продолжение: новый процесс Pi, `switch_session` на `pi_session_path`, промпт «продолжи с места остановки».
