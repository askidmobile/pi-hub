# Жизненный цикл задачи и вопросы воркера

Машина статусов закодирована в `packages/protocol/src/status.ts` (`TRANSITIONS`); менеджер сессий отклоняет любые другие переходы.

```
queued ─► planning (clarify) ─► needs_input ─(send)─► running
   │                                 ▲   │
   │                       ask       │   └─(рестарт хаба)─► interrupted
   └──────────► running ─────────────┘
                  │ agent_settled (вопрос текстом → needs_input)
                  ▼
               checking ─► done ─(send: доработка)─► running
                  │  ▲
                  │  └─ авто-круг: FAIL с новыми ошибками → running → checking (один раз)
                  │  └─ эскалация: снова FAIL → новая модель роли → running → checking
                  └──► failed ─(send)─► running

любой активный и needs_input ─► cancelled (cancel, worktree сохраняется, вопрос закрыт)
running/planning/checking/needs_input ─► interrupted (рестарт хаба) ─► running (switch_session)
активный без владельца > orphan_after_minutes ─► orphaned ─► adopt
```

`done` значит «готово к слиянию», но не необратимо: `send` возвращает задачу на доработку в той же сессии Pi и ветке, с новой финализацией и проверкой; `attempt` растёт. Если ветка уже слита, `send` предупреждает «ветка уже слита: новые коммиты нужно слить заново».

## Доставка вопроса (этап 2)

1. Воркер вызывает инструмент `ask(question, options?)` из расширения pi-hub.
2. Расширение открывает `ctx.ui.input` с заголовком `pi-hub:ask <json>`. В RPC-режиме Pi пишет в stdout `extension_ui_request {id, method: "input", title}` и **ждёт** — токены не тратятся. Диалоги без маркера хаб отклоняет.
3. `WorkerRun` записывает вопрос в `questions` (`round`, `kind`, `options_json`, `pi_dialog_id`) и переводит задачу в `needs_input`. Процесс Pi живёт; таймер длительности, если задан, на паузе; слот воркера освобождается.
4. Старшему вопрос доходит тремя путями: `wait` возвращается сразу с вопросом; к ответу любого инструмента сессии добавляется строка «ожидают ответа: t_0142 (1 вопрос) — ответьте через send»; хук `Stop` (`pi-hub-shim hook stop`) один раз блокирует завершение хода с текстом вопроса.
5. `send(task_id, message)` → `extension_ui_response {id, value}` → расширение возвращает ответ воркеру; вопрос закрыт (`answered_by = senior`), задача снова `running`.
6. Консультанта нет, System One вопросы воркера не оценивает: все вопросы идут старшему.

Фаза плана (`clarify`) — тот же механизм: первое сообщение просит прочитать код, ничего не менять и закончить фазу одним `ask` с планом и вопросами; ответ ведёт в `running` в той же сессии. Если в фазе плана изменились файлы, к плану добавляется предупреждение. Фаза, закончившаяся текстом без `ask`, тоже становится вопросом-планом.

**Вопрос текстом** (воркер спросил в итоговом сообщении, без `SUMMARY:`, последний абзац с «?»): хаб оформляет его как вопрос `kind = text`, ответ уходит новым `prompt` в тот же процесс. Задача не отменяется.

**Хук Stop** находит свою сессию по предкам процесса (`claude → sh → pi-hub-shim hook stop`, MCP-shim той же сессии — ребёнок того же `claude`; у Codex — `codex`, команда с `--client codex`); запасной путь — единственная подключённая сессия того же клиента в проекте. Не блокирует при режиме `off`, при `stop_hook_active`, если хаб не отвечает или вопрос уже показан; решения — в `logs/hooks.log`.

## Проверка качества

После финализации (`checking`) хаб выполняет команды `.pi-hub.toml` (`quality.test/lint/typecheck`) и ставит `PASS`/`FAIL`/`SKIPPED`. Ошибки, которые были и на коммите базы, помечаются «падало до задачи»; на новые ошибки — один авто-круг исправления в той же сессии Pi. Подробно — ADR-0012.

## Выбор модели и эскалация (этап 3)

**Модель задачи** при `start` выбирается по порядку:
1. Модель, которую указал старший.
2. Роль, которую указал старший.
3. Умный роутер. Только если включён `router.smart`, задан `system_one` и ролей ≥ 2: System One выбирает роль по описаниям. Ниже порога уверенности — `default_role`.
4. `default_role`.

Источник выбора — `tasks.routed_by` (`architect`, `rules`, `system_one`) и причина. Сбой System One не блокирует задачу: работают правила, в причине `system_one_unavailable`. Подробно — ADR-0008.

**Эскалация.** Если после авто-круга проверка снова `FAIL` с новыми ошибками, хаб останавливает Pi и запускает новый процесс на следующей модели из `escalate` роли — в той же задаче, worktree и ветке. Первое сообщение начинается с `ESCALATION:`: задача, итог прошлой модели и замечания проверки. Цикл тот же: работа, финализация, проверка, авто-круг. Старший продолжает `wait` и получает одну задачу:
- в конверте — `models` и предупреждение «эскалировано: A → B»;
- в `pi-hub status` — модель последнего прогона с «↑».

Эскалации нет, если:
- модель выбрал старший;
- ошибки были на базе;
- цепочка закончилась;
- это `send` на `done`/`failed`.

Каждый прогон модели — строка `task_model_runs`. Подробно — ADR-0013.

## `wait` и таймауты клиентов

`wait(task_id, timeout)` — длинный опрос. Хаб обрезает `timeout` до `min(запрошенный, client_tool_timeout − запас)` и возвращает текущий статус, если ничего не произошло. Таймаут клиента берётся из конфига плагина (Codex: `tool_timeout_sec`). См. ADR-0006.

## Перезапуск хаба

При старте: все задачи в `running|planning|checking|needs_input` без живого запуска → `interrupted`; открытый вопрос остаётся открытым. Продолжение — `send`: новый процесс Pi, `switch_session` на `pi_session_path`; если был открытый вопрос, воркер получает текстом «вопрос — ответ».
