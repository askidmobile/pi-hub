# Архитектура pi-hub

Статус: черновик v0.1 (2026-11-26). Источник требований — [спецификация](../spec/pi-hub-spec.md).
Решения с обоснованием — в [ADR](../adr/). Стек — [stack.md](stack.md). Жизненный цикл задачи — [task-lifecycle.md](task-lifecycle.md).

## Процессы

```
 машина пользователя                               машина хаба (та же или build-box)
┌───────────────────────────┐                     ┌──────────────────────────────────────────────┐
│ Claude Code / Codex       │                     │ pi-hub daemon (Node.js, один процесс)         │
│  ├─ MCP stdio ─► shim ────┼── unix-сокет ──────►│  transport ─► MCP-фасад (Server на соединение)│
│  │                        │   или ssh stdio     │      │                                        │
│  └─ хуки SessionStart/Stop┼── pi-hub hook ─────►│  менеджер сессий ◄─► хранилище (SQLite WAL)   │
└───────────────────────────┘                     │      │            учёт     роутер ─► System One│
                                                  │      ▼                                        │
                                                  │  RPC-клиент Pi ──stdin/stdout JSONL──► pi    │
                                                  │  менеджер worktree    проверка качества       │
                                                  └──────────────────────────────┬───────────────┘
                                                                                 │ один процесс Pi на задачу
                                                                    pi --mode rpc (cwd = worktree, ключи из env)
                                                                     └─ расширение pi-hub: ask, report_assumption
```

- **shim** — прозрачная труба: пересылает кадры MCP JSON-RPC между stdio клиента и хабом, добавив в начало одно сообщение `Hello` (ADR-0002). MCP-сервер живёт в хабе, поэтому `tools/list_changed`, права и режим целиком на стороне хаба.
- **хуки** вызывают `pi-hub hook …` — короткую CLI-команду, которая за ≤ 100 мс спрашивает хаб через тот же сокет и при любой ошибке выходит с 0.
- **воркер** — `pi --mode rpc` в своём worktree. Вопросы приходят хабу через подпротокол Extension UI Pi по тому же stdout (ADR-0005).

## Компоненты хаба (`packages/hub/src`)

| Модуль        | Ответственность                                                                                       | Ключевые зависимости  |
| ------------- | ----------------------------------------------------------------------------------------------------- | --------------------- |
| `transport/`  | unix-сокет (0600), Streamable HTTP на 127.0.0.1, рукопожатие и версия протокола                       | `@pi-hub/protocol`    |
| `facade/`     | экземпляр MCP `Server` на соединение; список инструментов по режиму; подвал ответа (вопросы, бюджет)  | MCP SDK               |
| `sessions/`   | старшие сессии, владение, машина статусов, сироты, восстановление после рестарта, квоты процессов     | storage               |
| `pi-rpc/`     | запуск Pi, JSONL-кадрирование, события → журнал + учёт, Extension UI → вопросы                        | Pi `RpcClient` / типы |
| `workspaces/` | `git worktree add -b pi/<task_id>`, список изменений, проверка конфликтов (`git merge-tree`), очистка | git CLI               |
| `quality/`    | тесты/линтер/типы из `.pi-hub.toml`, блокировка сборки на проект, вердикт PASS/FAIL/SKIPPED           | —                     |
| `router/`     | роль → модель, System One, эскалация, «липкая» смена модели                                           | `system-one/` адаптер |
| `accounting/` | запись `steps`, цены, бюджеты 80/100 %, строка стоимости, `usage_report`                              | storage               |
| `storage/`    | `node:sqlite`, миграции по `schema_version`, JSONL-журналы задач                                      | —                     |
| `notify/`     | уведомления пользователю (сироты, молчание старшего, бюджет)                                          | —                     |
| `cli/` | `pi-hub serve\|init\|doctor\|status` (этап 1); `hook\|token\|report` — следующие этапы | commander, `@inquirer/prompts` |

Внутри процесса модули общаются через типизированную шину событий (`task.status_changed`, `task.question`, `step.recorded`) — её же позже читает веб-панель.

## Основной сценарий

1. Старший вызывает `start`. Фасад проверяет режим (`off` → отказ), права токена, бюджет и квоты.
2. Роутер выбирает роль и модель; решение пишется в `tasks.routed_by/route_reason`.
3. Менеджер worktree создаёт ветку `pi/<task_id>` от `base_branch`.
4. RPC-клиент запускает Pi с моделью, `--session-dir` хаба и расширением pi-hub; отправляет промпт воркера.
5. События Pi пишутся в `logs/<task_id>.jsonl`; `message_end.usage` → `steps`.
6. Вопрос воркера (`ask`) → `extension_ui_request` → System One решает: консультант или старший → статус `needs_input`, ожидающий `wait` возвращается.
7. `agent_settled` → проверка качества (`checking`) → `done`/`failed`; при двух FAIL подряд — эскалация.
8. `wait`/`result` отдают конверт (`ResultEnvelope`) и строку стоимости.

## Сквозные требования

- **Идентификаторы:** `task_id` (`t_0142`) и `senior_session_id` во всех логах shim, хаба, хуков и в журнале Pi (имя сессии Pi = `task_id`).
- **Безопасность:** ключи только в env процесса Pi; маскирование секретов в журналах по шаблонам; список разрешённых репозиториев; хаб не слушает внешние интерфейсы.
- **Устойчивость:** хуки никогда не блокируют старшего; падение хаба → задачи `interrupted`, продолжение через `switch_session` с сохранённым путём сессии Pi.
- **Экономия токенов старшего:** 8 инструментов с короткими описаниями; в режиме `off` — один.

## Что сознательно отложено

Веб-панель, Postgres и несколько хабов, еженедельная подстройка таблицы ролей, «липкая» смена модели внутри сессии по оценке выгоды — после MVP (см. [roadmap](../brief/PROJECT-BRIEF.md#9-этапы)).
