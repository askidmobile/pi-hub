# ADR-0006. `wait` — длинный опрос с потолком по клиенту

**Статус:** Предложено, уточнено 2026-11-26 (OQ-13).

**Контекст.** У клиентов MCP есть таймауты вызова инструмента. Вызов, висящий дольше, обрывается с ошибкой. Каждый повторный `wait` стоит старшему токенов, поэтому потолок выгодно держать как можно выше.

Таймауты клиентов (документация, 2026-11-26):

| Клиент | Таймаут вызова | Таймаут простоя | Запуск сервера | Progress-уведомления |
|---|---|---|---|---|
| Claude Code | `MCP_TOOL_TIMEOUT`, по умолчанию 100 000 000 мс (~28 ч); `timeout` в мс на сервер в `.mcp.json` | `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`: для stdio 30 мин, для HTTP 5 мин | `MCP_TIMEOUT`, 30 с | сбрасывают таймаут простоя, но не общий `timeout` |
| Codex | `tool_timeout_sec`, по умолчанию 60 с, задаётся на сервер | — | `startup_timeout_sec`, 10 с | влияние не описано |

**Решение.**

- Потолок `wait` задаётся по клиенту в конфиге хаба (`clients.<kind>.max_wait_sec`); хаб обрезает запрошенный `timeout` до него и по истечении возвращает текущий статус.
- **Claude Code:** в `.mcp.json` плагина `timeout = 1 800 000` мс (30 мин); `max_wait_sec = 1500` (25 мин). Во время `wait` хаб шлёт progress-уведомление раз в 60 с — это держит таймаут простоя.
- **Codex:** в профиле `tool_timeout_sec = 900`; `max_wait_sec = 870` (запас 30 с).
- **Неизвестный MCP-клиент:** считаем, что таймаут 60 с; `max_wait_sec = 50`.
- Остальные инструменты отвечают быстро (< 1 с); большой таймаут на них не влияет.
- Shim стартует и отвечает на `initialize` без ожидания хаба (запуск MCP-сервера в Codex ограничен 10 с). Если хаб недоступен, инструменты возвращают понятную ошибку, а не висят.
- Скил архитектора: «если `wait` вернул `running` — снова `wait`».

**Последствия.** Типичная задача воркера (5–15 мин) укладывается в один-два вызова `wait`. Значения перепроверяются при обновлении клиентов; `pi-hub doctor` показывает действующий потолок.
