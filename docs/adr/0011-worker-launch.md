# ADR-0011. Запуск воркера Pi: изолированная конфигурация и расширение pi-hub

**Статус:** Предложено (2026-11-26). Закрывает OQ-15. Подтверждает ADR-0005 живой проверкой.

## Контекст

Воркер должен получать расширение pi-hub (`ask`, `report_assumption`) и не должен подхватывать личную настройку Pi на машине хаба: глобальные расширения (`~/.pi/agent/extensions`, например роутеры моделей), пакеты из `settings.json`, глобальный `AGENTS.md`, MCP-серверы. Иначе хаб теряет контроль над моделью, стоимостью и поведением.

Факты (документация Pi и проверка на Pi 1.6.1, 2026-11-26):

- `-e, --extension <path>` загружает файл или каталог расширения, повторяемый; TypeScript грузится через jiti без сборки.
- `-ne, --no-extensions` отключает найденные, настроенные и встроенные расширения; явные `-e` всё равно грузятся.
- `--no-mcp` отключает встроенный MCP; `-na, --no-approve` игнорирует локальные файлы проекта (`.pi/` репозитория); `-nc` отключает `AGENTS.md`/`CLAUDE.md`.
- `--append-system-prompt <text|path>` дописывает системный промпт; `--model` принимает `провайдер/id[:уровень]`.
- `PI_CODING_AGENT_DIR` переопределяет каталог конфигурации (по умолчанию `~/.pi/agent`); `PI_OFFLINE=1` отключает сетевые запросы при старте, включая обновление каталога моделей.
- Pi сам подставляет расширениям свои `@earendil-works/pi-coding-agent`, `pi-ai`, `typebox` — их не надо класть в зависимости расширения.
- **Проверено:** `pi --mode rpc --no-session -ne -e ext.ts --no-mcp -na` с `PI_CODING_AGENT_DIR` во временном каталоге — загрузилось только тестовое расширение; `ctx.ui.select` пришёл хабу как `extension_ui_request {method: "select", title, options}`, ответ `extension_ui_response {id, value}` вернулся в расширение. Модель для этого не нужна.

## Решение

Хаб запускает воркера так:

```
cwd = <worktree задачи>
env = PI_CODING_AGENT_DIR=~/.pi-hub/pi-agent   # конфиг Pi, которым владеет хаб
      PI_OFFLINE=1                              # каталог моделей не меняется между обновлениями Pi
      <ключ только выбранного провайдера>       # из ~/.pi-hub/.env
pi --mode rpc
   --model <провайдер/id>[:<уровень>]
   --session-dir ~/.pi-hub/sessions --name <task_id>
   -ne -e <путь к @pi-hub/pi-extension>
   --no-mcp -na
   --append-system-prompt <промпт воркера для задачи>
```

- `~/.pi-hub/pi-agent` — отдельный каталог конфигурации Pi: хаб пишет туда свой `settings.json` (`defaultTools` и т.п.), личный `~/.pi/agent` не используется. Ключи провайдеров приходят только через окружение.
- `AGENTS.md` целевого репозитория **загружается** (без `-nc`): это правила проекта, воркеру они нужны. Глобальный `AGENTS.md` пользователя не попадает, потому что каталог конфигурации свой.
- MCP у воркеров выключен по умолчанию; проект может включить его в `.pi-hub.toml`, если воркерам нужен конкретный сервер.
- Расширение pi-hub поставляется в составе хаба как каталог пакета (`packages/pi-extension`); путь хаб находит сам. Зависимости Pi не перечисляются в `dependencies` расширения.
- Промпт воркера (`packages/pi-extension/worker-prompt.md`) рендерится на задачу и передаётся через `--append-system-prompt`, не заменяя системный промпт Pi.

## Последствия

- Поведение воркера воспроизводимо: одинаковые расширения, инструменты и каталог цен на всех машинах хаба.
- Обновление Pi = обновление каталога цен; хаб импортирует цены после обновления (BD-016).
- `pi-hub doctor` проверяет: версия Pi совпадает с закреплённой, `-e` путь существует, расширение регистрирует `ask` (через RPC `get_commands`/список инструментов без вызова модели).
