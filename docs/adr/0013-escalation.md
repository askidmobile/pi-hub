# ADR-0013. Эскалация: следующая модель роли в той же задаче

**Статус:** Принято (2026-11-27). Этап 3: [спецификация](../specs/2026-11-27-stage-3-routing-codex.md) FR-201…FR-205, FR-230; решения D-201, D-202, D-203, D-211, D-215; план PD-205.

## Контекст

Дешёвая модель иногда не справляется даже после авто-круга (ADR-0012). Если отдать `FAIL` старшему, он тратит дорогие токены: читает замечания, перезапускает задачу, выбирает модель. Обычно выгоднее, чтобы хаб сам передал ту же работу модели сильнее и вернул старшему готовый результат.

## Решение

- **Цепочка.** У роли в `config.yaml` есть необязательный список `escalate`: модели в порядке попыток. Следующая модель — первая из списка, которая на этой задаче ещё не работала (`router/escalation.ts`, `nextModel`).
- **Когда.** Вторая подряд `FAIL`-проверка с новыми ошибками, то есть `FAIL` после авто-круга (D-201). Нет эскалации, если:
  - все ошибки были и на базе;
  - модель выбрал старший (D-211);
  - цепочка пустая или закончилась;
  - задачу отменили;
  - это `send` на `done`/`failed`: решение уже у старшего.

  `send` на `interrupted` доводит прерванный запуск так, как он шёл бы, поэтому может эскалировать.
- **Как.** Внутри одного `WorkerRun` (PD-205): процесс Pi останавливается, в том же worktree и на той же ветке запускается новый процесс Pi на следующей модели (D-202, D-203). Первое сообщение начинается с `ESCALATION:`: в нём задача, итог прошлой модели и замечания проверки. Дальше путь тот же: работа → финализация → проверка → авто-круг. Для старшего это одна задача, `wait` не возвращается до итога.
- **История.** Каждая модель — строка `task_model_runs` (`seq`, `model`, `routed_by`, `reason`, начало и конец, вердикт). Стоимость шагов всех моделей суммируется в задаче.
- **Старшему.** В конверте `models` — все модели по порядку, и предупреждение «эскалировано: A → B (FAIL после авто-круга)». В `pi-hub status` — модель последнего прогона и по «↑» на каждую эскалацию (FR-230).
- **PASS с первого раза.** `tasks.first_try_pass`:
  - 1 — первая проверка первой модели `PASS`;
  - 0 — первая проверка `FAIL`;
  - `NULL` — без проверки (`SKIPPED` не входит в долю, D-215).

  Это основа доли в `usage_report` и в эталонах.

## Последствия

- Задача, которую дешёвая модель не довела, доходит до старшего готовой. Цена — ещё один запуск воркера на модели дороже.
- Сильная модель наследует коммиты слабой. Исправить дешевле, чем переписать, но неудачные решения переходят дальше. Защита тестов (ADR-0012) действует и после эскалации.
- Порядок цепочки — решение автора по [эталонному прогону](../../benchmarks/results/2026-11-27.md). Три лучшие модели там упёрлись в потолок, поэтому порядок нужно пересматривать по данным `usage_report`.
- Известное ограничение: кэш проверки базы привязан к имени команды, а не к её тексту (TD-201).
