# ADR-0004. Pi как дочерний процесс в режиме RPC

**Контекст.** Нужны изоляция задач, отмена, смена модели, учёт токенов и восстановление после рестарта. Pi предлагает SDK (в процессе) и RPC (дочерний процесс).

**Решение.** Один `pi --mode rpc` на задачу, `cwd` = worktree, ключи только в env процесса, `--session-dir` в каталоге хаба, имя сессии = `task_id`. Свой тонкий `PiRpcClient` (~250 строк, `packages/hub/src/pi-rpc/`): JSONL-кадрирование только по LF без `readline`, корреляция ответов по `id`, zod-разбор нужного подмножества событий; пакет Pi в зависимости хаба не входит (план этапа 1, PD-001). Версия Pi закреплена в конфиге хаба.

**Последствия.** Падение воркера не роняет хаб; при рестарте хаба процессы умирают — статус `interrupted` и продолжение через `switch_session`. Контрактные тесты на записанных JSONL-сессиях ловят изменения формата при обновлении Pi.

**Дополнение (2026-11-26, этап 1).** Выбран свой клиент, а не экспортируемый `RpcClient` Pi: хаб не зависит от пакета Pi и его транзитивных зависимостей, фейковый воркер (`packages/fake-worker`) подключается тем же путём, что и настоящий Pi, а изменения формата ловит контрактный тест на записанной сессии (`packages/hub/test/fixtures/pi-session-success.jsonl`). Проверено сквозным прогоном `pnpm e2e` на Pi 1.6.1.
