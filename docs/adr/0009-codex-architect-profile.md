# ADR-0009. Режим архитектора в Codex — файл профиля, без отдельного CODEX_HOME

**Статус:** Предложено (2026-11-26). Закрывает OQ-06.

## Контекст

Уровень 1 спецификации: обычный Codex не должен видеть pi-hub вообще, режим архитектора запускается отдельно. Варианты: отдельный `CODEX_HOME` или профиль.

Факты (Codex CLI 0.171.0, проверено на практике во временном `CODEX_HOME`):

- Профиль — отдельный файл `$CODEX_HOME/<name>.config.toml`, накладывается поверх `config.toml` при `--profile <name>`. Таблицы `[profiles.x]` внутри `config.toml` не читаются с 0.134.0.
- **Файл профиля принимает `mcp_servers`:** `codex --profile arch mcp list` показывает сервер из профиля, без профиля — нет.
- `[hooks]` в файле профиля разбирается без ошибок; хуки — стабильная функция, включены по умолчанию (`codex features list`: `hooks stable true`). Реальный запуск `codex exec --profile ...`: хуки из профиля **не сработали**, потому что не доверены. Codex выполняет только хуки, у которых в `~/.codex/config.toml` есть запись `[hooks.state."<id>"]` с `trusted_hash`; недоверенные в `exec` пропускаются молча. Доверие ставит пользователь в `/hooks` интерактивной сессии.
- Отдельный `CODEX_HOME` — это отдельные `auth.json` (при файловом хранении — повторный вход), история, сессии, кэши.
- Проектный `.codex/config.toml` игнорирует `profile`/`profiles` и загружается только для доверенных проектов.
- Любой ключ переопределяется флагом `-c`, например `-c mcp_servers.pi-hub.enabled=true`.

## Решение

- Режим архитектора — профиль `~/.codex/pi-hub.config.toml` (`plugins/codex/pi-hub.config.toml`): `[mcp_servers.pi-hub]` и хуки SessionStart/Stop. Запуск `codex --profile pi-hub`, алиас `codex-arch`.
- Отдельный `CODEX_HOME` не используем: тот же вход, история и сессии, что у обычного Codex.
- Запасной вариант, если хуки профиля не срабатывают: хуки в `~/.codex/hooks.json`. Они вызываются во всех сессиях Codex, но за < 100 мс выходят, если у сессии нет shim pi-hub (токенов не тратят).
- `tool_timeout_sec` для pi-hub задаётся в профиле и используется как потолок `wait` (ADR-0006, OQ-13).

## Последствия

- Обычный `codex` не видит pi-hub — нулевая цена для старшего.
- Установка плагина Codex = копирование одного файла; `pi-hub init` может делать это сам.
- Установка требует одного ручного шага: открыть `codex --profile pi-hub`, выполнить `/hooks` и доверить два хука pi-hub. `pi-hub init` подсказывает это и не ставит доверие сам: это решение пользователя о безопасности. После изменения команды хука доверие нужно подтвердить заново (меняется хеш).
- `pi-hub doctor` проверяет, есть ли для хуков pi-hub запись `trusted_hash`, и подсказывает, если нет.
- **Проверено (2026-11-26):** при первом интерактивном запуске с профилем Codex сам спрашивает о доверии папке и новым хукам. После доверия оба хука срабатывают (SessionStart на первом промпте, Stop в конце хода).
- **Доверие хранится в самом файле профиля:** Codex дописывает в `pi-hub.config.toml` секции `[hooks.state."<путь профиля>:<событие>:0:0"] trusted_hash = …` и `[projects."<папка>"] trust_level = "trusted"`. Поэтому `pi-hub init` и обновления **не перезаписывают** файл профиля целиком, а меняют только свои ключи и сохраняют `hooks.state` и `projects`. Изменение команды хука сбрасывает доверие (другой хеш).

## Данные хуков Codex (фактический вход)

- SessionStart: `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, `permission_mode`, `source` (`startup`).
- Stop: те же поля плюс `turn_id`, `stop_hook_active`, `last_assistant_message`; без `source`.

## Инструкция по запуску

1. Скопировать профиль: `~/.codex/pi-hub.config.toml` (или `pi-hub init` сделает это сам).
2. Один раз запустить `codex --profile pi-hub` в папке проекта.
3. Разрешить папку проекта и два хука pi-hub, когда Codex спросит.
4. Дальше работать через `codex --profile pi-hub` (алиас `codex-arch`).

## Дополнение (2026-11-27, этап 3)

Что реализовано на этапе 3 (FR-207…FR-210, D-207, D-208, D-212, D-216; план PD-201, PD-208, PD-211, PD-213). Проверено на Codex 0.172.

- **Только хук Stop.** SessionStart не нужен (D-212, PD-211): хук Stop находит сессию хаба по предкам процесса. MCP-сервер и хук — дети одного процесса `codex`. Команда хука — `pi-hub-shim hook stop --client codex`.
- **Блок между метками** (PD-201, D-216): `pi-hub init` пишет в `~/.codex/pi-hub.config.toml` только текст между `# >>> pi-hub` и `# <<< pi-hub`.
  - Перед изменением — копия `.bak`. Результат проверяется разбором TOML.
  - Профиль с pi-hub без меток, повреждённые метки или неразбираемый результат — отказ без изменения файла.
  - Codex дописывает `[hooks.state…]` и `[projects…]` перед последним комментарием файла, то есть внутрь блока. `init` сохраняет такие таблицы и переносит их за закрывающую метку, поэтому доверие не сбрасывается.
- **Режим при подключении выключен** (D-207), как у всех клиентов. Совет ADR-0010 включать его для Codex отменён.
- **Скил архитектора** (PD-213): `init` ставит `~/.codex/skills/pi-hub-architect/SKILL.md`, а при замене изменённого файла делает копию `.bak`. В скиле правила:
  - вопросы пользователю — штатной формой Codex (`request_user_input`), без `wait` до ответа;
  - роль — только из таблицы хаба.
- **`doctor`** проверяет профиль, доверие к хуку (запись `hooks.state` с учётом собственных хуков Stop пользователя) и актуальность скила.
- **Ручной шаг остаётся:** доверить хук в `codex --profile pi-hub` → `/hooks`. `init` подсказывает это и доверие не ставит.
