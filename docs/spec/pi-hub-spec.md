# pi-hub: спецификация

Nov 26, 2026 · @Fatima

pi-hub это локальный или удалённый демон, через который старший агент (Codex, Claude Code или любой MCP-клиент) поручает работу младшим агентам Pi на дешёвых моделях: DeepSeek, GLM, Kimi, локальных. Старший планирует, ставит задачи и принимает результат, младшие пишут код в изолированных ветках. Старший получает короткую сводку вместо полного хода работы, поэтому дорогие токены тратятся только на проектирование и приёмку.

Ключевые решения: ядро хаба не зависит от платформы, а к каждому клиенту подключается тонкий плагин; состояние хранится в SQLite; режим делегирования выключен по умолчанию и включается явно; каждая задача принадлежит своей старшей сессии; модель выбирается по роли задачи, в том числе с помощью System One модели; хаб ведёт учёт токенов и стоимости по каждому шагу.

## Назначение и границы

Цель: сократить расход дорогой модели старшего агента, перенести исполнение на дешёвые модели и при этом сохранить контроль над качеством, стоимостью и безопасностью.

**Входит:**

- запуск и сопровождение сессий Pi: старт, ожидание, вопросы, продолжение, отмена;
- изоляция задач в git worktree и отдельных ветках;
- краткая сводка для старшего и полный журнал на диске;
- проверка качества после задачи: тесты, линтер, типы;
- маршрутизация моделей по ролям и эскалация;
- многосессионная работа с несколькими клиентами одновременно;
- учёт токенов и стоимости, бюджеты и квоты;
- работа на удалённой машине для сборок и тестов;
- тонкие плагины для Codex и Claude Code.

**Не входит:**

- собственный агент или модель: исполнителем служит Pi;
- собственный шлюз к провайдерам: доступ идёт напрямую, через OpenRouter или OrcaRouter;
- песочница уровня ОС: изоляция обеспечивается окружением (пользователь, контейнер, ВМ);
- автономные «компании агентов» с оргструктурой, как в Paperclip: главным остаётся старший агент пользователя.

## Архитектура

Ядро живёт в одном демоне, а каждая старшая сессия подключается к нему через свой тонкий shim. Плагины платформ не содержат логики и ключей.

Каждый воркер это отдельный процесс Pi в своём worktree; ключи провайдеров и состояние есть только на машине хаба.

## Компоненты

Хаб состоит из девяти компонентов в одном процессе Node.js; воркеры Pi работают отдельными процессами. Язык реализации TypeScript: на нём написаны Pi, его SDK и официальный MCP SDK.

| Компонент | Отвечает за |
| --- | --- |
| Shim (прослойка) | Отдельный маленький процесс на каждую старшую сессию. Говорит с агентом по MCP через stdio, с хабом через unix-сокет или HTTP. Передаёт тип клиента, id сессии и проект. |
| MCP-фасад | Набор инструментов, видимых конкретному соединению, с учётом режима и прав. Уведомление о смене списка инструментов. |
| Менеджер сессий | Жизненный цикл задач, статусы, владение, сироты, восстановление после перезапуска. |
| RPC-клиент Pi | Запуск Pi в режиме RPC, один процесс на задачу. Чтение событий, отправка сообщений, смена модели и уровня рассуждения. |
| Менеджер рабочих областей | git worktree и ветка на задачу, список изменённых файлов, проверка конфликтов между ветками, очистка. |
| Проверка качества | Тесты, линтер и проверка типов по изменённым файлам. Вердикт PASS, FAIL или SKIPPED. |
| Роутер | Выбор модели по роли, вызов System One модели, эскалация, решение о смене модели внутри сессии. |
| Учёт | Запись шагов (токены, стоимость, задержка), бюджеты, квоты, отчёты. |
| Хранилище | SQLite для метаданных, JSONL-журналы на диске, миграции схемы. |

По желанию добавляется веб-панель: она только читает базу и поток событий и нужна человеку, а не агенту.

## Протокол MCP

Старшему доступно семь инструментов вместо двадцати: каждое описание инструмента оплачивается токенами в каждой сессии. В выключенном режиме виден только `architect_mode`.

| Инструмент | Что делает | Возвращает |
| --- | --- | --- |
| `start(task, role?, model?, repo, base_branch, clarify?)` | Создаёт задачу, worktree и сессию Pi, не ждёт завершения | `task_id`, статус, выбранная модель и причина выбора |
| `wait(task_id, timeout)` | Блокирует до таймаута, завершения или вопроса воркера | статус, сводка или текст вопроса |
| `status(scope?)` | Список своих задач; чужие только с правом администратора | задачи со статусами и стоимостью |
| `send(task_id, message)` | Ответ на вопрос или продолжение в той же сессии Pi | новый статус |
| `result(task_id)` | Итог задачи | конверт со сводкой (ниже) |
| `cancel(task_id)` | Остановка задачи, worktree сохраняется | статус `cancelled` |
| `usage_report(scope, period)` | Отчёт по токенам и стоимости за сессию, проект или период | агрегаты |
| `architect_mode(on\|off)` | Включение и выключение режима для этой сессии по команде пользователя | текущий режим |

**Статусы задачи:** `queued`, `planning` (фаза вопросов), `running`, `needs_input`, `checking` (проверка качества), `done`, `failed`, `cancelled`, `interrupted` (хаб перезапустился), `orphaned` (владелец пропал). Из `needs_input` задача возвращается в `planning` или `running` после `send`; из `interrupted` и `orphaned` её можно продолжить с той же сессии Pi.

**Конверт результата.** Старший читает только его; полный журнал открывается только при сбое.

```json
{
  "task_id": "t_0142",
  "status": "done",
  "summary": "Добавлена валидация формы регистрации, 12 тестов",
  "assumptions": ["Длина пароля не менее 10 символов"],
  "branch": "pi/t_0142",
  "changed_files": ["src/forms/register.ts", "tests/register.test.ts"],
  "quality": {"status": "PASS", "issues": []},
  "usage": {"cost_usd": 0.043, "input": 182000, "cached_share": 0.71, "output": 9000, "minutes": 6},
  "session_total_usd": 0.31,
  "log_path": "~/.pi-hub/logs/t_0142.jsonl"
}
```

К ответу любого инструмента добавляется строка о вопросах, ожидающих ответа у этой сессии, и предупреждение о бюджете, если он израсходован на 80% и более.

## Вопросы воркера

MCP работает по схеме «запрос и ответ», и воркер не может прервать старшего посреди его хода. Поэтому доставка вопросов собрана из семи приёмов, в порядке важности.

1. **Фаза вопросов до работы.** При `clarify` воркер сначала читает код и возвращает план и вопросы с вариантами («A: Redis, B: БД»). Выполнение начинается после ответа старшего.
2. **`wait` возвращается на вопросе.** Когда старшему нечего делать, он висит в `wait`. Вопрос воркера сразу завершает ожидание со статусом `needs_input`. Ожидающий воркер токенов не тратит.
3. **Вопросы в каждом ответе хаба.** Если старший занят другим, любой вызов инструмента вернёт строку «ожидают ответа: t\_0142, 1 вопрос».
4. **Хук на завершение хода.** Перед тем как старший закончит ход, хук спрашивает хаб и при наличии вопросов не даёт ему остановиться, передавая вопрос. Это ближайший к прерыванию механизм.
5. **Мелкое воркер решает сам.** Правило в промпте воркера: некритичное решение принять, записать в `assumptions` и продолжить. Останавливаться только на схеме данных, публичном API, удалении и подобном.
6. **Консультант.** У воркера есть инструмент `ask` к более сильной дешёвой модели вместе со спецификацией задачи. System One модель оценивает, критичен ли вопрос: критичный идёт к старшему, остальные к консультанту.
7. **Пользователь как последняя инстанция.** Если старший не отвечает дольше заданного времени, хаб шлёт уведомление пользователю.

Если воркер нарушил протокол вопросов, задача отменяется и перезапускается: исходная задача и история ответов передаются новому промпту обычным текстом.

## Режимы и согласие пользователя

Режим делегирования выключен по умолчанию, и запрет держит хаб, а не промпт: при выключенном режиме любой вызов делегирования отклоняется.

| Уровень | Как работает | Цена для старшего |
| --- | --- | --- |
| 1. Не подключено | Обычный запуск агента без хаба. Режим архитектора запускается отдельно: профиль Codex, отдельный `CODEX_HOME`, отдельный конфиг MCP для Claude Code, алиас `codex-arch`. | ноль |
| 2. Подключено, выключено | Виден один инструмент `architect_mode`. Хуки проверяют флаг и сразу выходят. | описание одного инструмента |
| 3. Включено | Команда `/architect on` или настройка проекта. Хаб шлёт уведомление о смене списка инструментов и открывает остальные. | восемь инструментов и скил |

**Область действия режима**, срабатывает самая узкая:

- сессия: `/architect on|off` в окне, выключается при выходе;
- проект: `delegation: on` в AGENTS.md или `.pi-hub.toml` в корне репозитория;
- глобально: конфиг хаба, по умолчанию `off`.

`/architect off` запрещает новые задачи и спрашивает, что делать с запущенными: дать доработать или отменить. Описание скила узкое: «используй только если пользователь включил режим архитектора», чтобы он не подгружался сам.

## Многосессионность

Один хаб обслуживает много старших сессий разных клиентов и проектов одновременно, поэтому всё состояние привязано к старшей сессии, а не к хабу целиком.

**Идентификация.** Каждая старшая сессия запускает свой shim. При подключении shim передаёт тип клиента, id сессии агента и проект (корень git-репозитория и адрес remote). MCP не передаёт id сессии, поэтому его берём из хуков клиента (Claude Code передаёт `session_id` и `cwd`), а запасной ключ это PID родительского процесса агента, общий для shim и хуков одной сессии.

**Владение задачами.** Задача принадлежит сессии, которая её создала.

- Вопросы воркера идут только владельцу: в его `wait`, его ответы и его хук.
- Сессия видит и отменяет только свои задачи. Все задачи видны через `/workers all` и веб-панель с токеном администратора.
- **Сироты.** Если сессия не появлялась дольше заданного времени, её задачи доходят до конца или до первого вопроса и получают статус `orphaned`. Пользователь получает уведомление, любая сессия забирает задачу командой `/workers adopt <id>`.

**Квоты и общие ресурсы:**

| Ограничение | Уровень |
| --- | --- |
| Одновременные процессы Pi | хаб, проект, старшая сессия |
| Бюджет в день | проект, старшая сессия |
| Сборка и тесты | блокировка на проект или машину, остальные в очереди |
| Имена worktree и веток | содержат id задачи, столкновения исключены |

Клиент без хуков (просто MCP) работает в запасном режиме: вопросы доходят через `wait` и строку в ответах инструментов.

## Хранение данных

Метаданные хранятся в SQLite, тяжёлое в файлах. Пишет в базу только демон хаба: shim, хуки и панель обращаются к хабу, а не к базе.

| Данные | Где |
| --- | --- |
| Сессии, задачи, владельцы, статусы, вопросы, режимы, квоты, шаги учёта | SQLite, режим WAL |
| Поток событий и полный журнал задачи | JSONL-файл на задачу, в базе путь |
| История разговора Pi | файл сессии самого Pi, в базе путь |
| Код и диффы | git: ветка и worktree, в базе имя ветки |
| Ключи провайдеров | `.env` хаба, никогда не в базе |

```sql
senior_sessions(id, client, client_session_id, parent_pid, project_id,
                mode, connected_at, last_seen_at, token_id)
projects(id, repo_root, remote_url, default_mode, daily_budget)
tasks(id, owner_session_id, project_id, status, role, model,
      routed_by, route_reason, escalated_from_task_id,
      worktree_path, branch, pi_session_path, log_path,
      summary, quality_status, pid, created_at, finished_at)
questions(id, task_id, round, text, options_json, critical,
          answer, answered_by, asked_at, answered_at)
steps(id, task_id, seq, model, provider, input_tokens, output_tokens,
      cache_read_tokens, cache_write_tokens, cost, cost_source,
      latency_ms, tool_name, created_at)
prices(model, provider, input, output, cache_read, cache_write, valid_from)
tokens(id, name, scope_json, hash, created_at, revoked_at)
schema_version(version)
```

**Восстановление после перезапуска.** Процессы Pi через stdio умирают вместе с хабом. При старте хаб проверяет задачи со статусом `running`, мёртвые помечает `interrupted`; их можно продолжить с той же сессии Pi по пути из базы.

**Очистка.** Завершённые задачи старше N дней архивируются, журналы сжимаются или удаляются. Агрегаты учёта хранятся бессрочно. Переход на Postgres нужен только для нескольких хабов с общим состоянием.

## Маршрутизация моделей

Модель выбирается по роли задачи слоями, от бесплатного к платному. Решает хаб, Pi получает модель параметром.

1. **Роль задаёт старший** в `start(role=…)`. Он полностью понимает задачу, а пометка стоит пару токенов.
2. **Таблица правил** превращает роль в модель.
3. **System One модель** определяет роль, если старший её не указал. При уверенности ниже порога берётся `default_role`.
4. **Эскалация:** два FAIL подряд перезапускают задачу на следующей модели цепочки, старший получает уведомление.
5. **Подстройка по аналитике:** раз в неделю хаб предлагает правки таблицы по стоимости успешной задачи и доле PASS с первого раза. Принимает правки пользователь.

```yaml
roles:
  design: { model: kimi-k3, fallback: [glm-5.2] }
  analysis: { model: glm-5.2, fallback: [deepseek-v4-pro] }
  code: { model: deepseek-v4-flash, escalate: [deepseek-v4-pro] }
  review: { model: gpt-5.6-luna, fallback: [deepseek-v4-pro] }
  docs: { model: deepseek-v4-flash }
default_role: code
router:
  system_one: { model: jev-latest, min_confidence: 0.75 }
```

System One модель получает текст задачи и краткое описание репозитория и возвращает вероятности по типизированным вопросам: `role` (выбор из ролей), `complexity` (оценка), `needs_clarification` (да или нет), `risk` (low, medium, high). Сложность выше порога выбирает модель сильнее в той же роли, `needs_clarification` запускает фазу вопросов, `risk: high` требует ревью перед слиянием.

Та же модель принимает решения по ходу работы: критичен ли вопрос воркера, эскалировать ли после FAIL, застрял ли воркер по хвосту журнала, каков риск диффа. Хаб говорит с ней через один адаптер в формате `/v1/systemone`, поэтому облачный Jev, Microsoft-Decision-1, Cloudflare Clef или локальная открытая модель выбираются конфигом. Пороги уверенности подбираются на накопленных данных хаба.

**Смена модели внутри сессии Pi** разрешена с «липкостью»:

- уровень рассуждения меняется свободно на каждом запросе: модель та же, кэш сохраняется;
- модель меняется на границах фаз (планирование, реализация, самопроверка, документация) и по событиям (застрял, FAIL);
- смена оправдана, если ожидаемая выгода больше, чем `токены контекста × (цена без кэша − цена с кэшем)` новой модели плюс риск сбоя. Оценку выгоды может давать Jev Router, цену считает хаб.

Каждое решение записывается в `tasks.routed_by` (architect, rules, system\_one, escalation) и `route_reason`.

## Учёт и аналитика

Хаб записывает каждый вызов модели в таблицу `steps` и собирает из них отчёты по задаче, старшей сессии, проекту и периоду.

**Источники цифр**, по убыванию точности:

1. фактическая стоимость от провайдера (OpenRouter возвращает её в ответе);
2. токены от провайдера, включая попадания в кэш, умноженные на цену из таблицы `prices`;
3. события Pi с токенами и стоимостью.

Источник пишется в `cost_source`. У каждой записи сохраняется цена на момент шага, чтобы старые отчёты не менялись при смене тарифов.

**Отчёт старшему и пользователю:**

- в каждом ответе `wait` и `result` одна строка: `0,043 $ · 182k вход (71% из кэша) · 9k выход · 6 мин · PASS · по сессии 0,31 $`;
- в скиле архитектора правило: после каждого делегированного шага одной фразой сообщить пользователю стоимость шага и итог за сессию;
- `usage_report` отвечает на вопросы вроде «сколько потратили на проект за неделю» из базы;
- бюджет: на 80% предупреждение в ответах, на 100% отказ в новых задачах до решения пользователя.

**Метрики для решений:**

| Метрика | Для чего |
| --- | --- |
| Экономия против старшей модели (оценка) | обосновать схему цифрой |
| Стоимость успешной задачи по роли и модели | править таблицу ролей |
| Доля PASS с первого раза | качество модели на ваших задачах |
| Число вопросов и эскалаций | качество постановки задач архитектором |
| Доля попаданий в кэш | насколько удачно собираются промпты |
| Время ожидания ответа старшего | насколько воркеры простаивают |

Экономия считается как токены воркера, умноженные на цену старшей модели, и в отчётах помечается как оценка. Стоимость самого старшего хаб видит только там, где клиент отдаёт её через хуки или статус-строку. Тексты промптов хранятся с тем же сроком очистки, что журналы; числа хранятся бессрочно.

## Удалённая работа

Хаб и воркеры могут работать на сборочной машине, а старший агент на ноутбуке пользователя. Проект не копируется: между машинами ходят только git-коммиты и краткие отчёты.

1. На сборочной машине лежит постоянный клон репозитория. Зависимости, кэши сборки и тестовые базы живут там постоянно.
2. Задача получает ветку от `base_branch`, воркер пишет код и гоняет тесты рядом с кэшами.
3. Результат уходит через git push, старший смотрит дифф и сливает.
4. Незакоммиченные правки передаются через временную ветку `wip/…` или rsync.

**Транспорт:**

- stdio через ssh: `ssh build-box pi-hub-shim`, ничего не открыто наружу;
- HTTP (Streamable HTTP MCP) с токеном, только через SSH-туннель или VPN (Tailscale, WireGuard).

Исполнитель сборки даёт удалённое выполнение кода, поэтому хаб никогда не слушает открытый интернет. В ответ о сборке идут только вердикт, первые ошибки и путь к полному логу; артефакты остаются на сборочной машине. Секреты и `.env` на ней настраиваются один раз и через git не передаются.

## Безопасность и ключи

Pi выполняет любые команды с правами пользователя, поэтому главная защита это изоляция окружения, а проверки хаба лишь страхуют от случайных ошибок.

- **Изоляция.** Воркеры работают под отдельным пользователем ОС, в контейнере или ВМ, если в репозитории есть секреты или доступ к проду. Каждая задача пишет только в свой worktree.
- **Разрешённые папки.** Хаб создаёт задачи только в репозиториях из списка. Это удобство, а не граница безопасности.
- **Ключи провайдеров** (DeepSeek, OpenRouter, OpenAI, System One) живут только в `.env` на машине хаба и передаются процессу Pi через окружение. В плагинах, конфигах старшего агента и базе их нет.
- **Токены клиентов.** У каждого клиента свой токен с областью доступа к проектам; отдельный токен администратора для панели и `/workers all`. В базе хранятся только хеши.
- **Сеть.** Локально unix-сокет с правами только для владельца, удалённо только туннель или VPN.
- **Журналы** содержат код и промпты. Срок хранения настраивается, секреты из вывода команд маскируются по шаблонам.
- **Хуки** при недоступном хабе молча пропускают ход и никогда не блокируют работу старшего.

## Плагины для Codex и Claude Code

Плагин каждой платформы тонкий, около 50 до 100 строк: он только переводит механизмы платформы на протокол хаба. Вся логика живёт в хабе.

| Часть | Codex | Claude Code |
| --- | --- | --- |
| Подключение | `[mcp_servers.pi-hub]` в профиле архитектора, запуск shim | MCP-сервер плагина, запуск shim |
| Правила архитектора | скил и строка в AGENTS.md проекта | скил плагина |
| Хук вопросов | хук завершения хода в формате Codex | хук завершения хода |
| Команды | аналоги `/architect`, `/workers` | `/architect on\|off`, `/workers`, `/workers all`, `/workers adopt`, `/workers doctor` |
| Конфиг | адрес и токен хаба | адрес и токен хаба |

**Скил архитектора** задаёт рабочий цикл:

1. Код сам не писать, дробить работу на задачи с критериями готовности, не больше 3 до 4 подзадач в одной.
2. Указывать `role` в `start`, для проектирования включать `clarify`.
3. Ждать через `wait`, читать только сводку, допущения и список файлов.
4. При FAIL вернуть задачу через `send` с замечаниями.
5. Перед слиянием параллельных веток проверить конфликты.
6. После каждого шага одной фразой сообщить пользователю стоимость.

**Требования к хукам:** ответ быстрее 100 мс, первым делом проверка режима, при любой ошибке пропуск хода и запись в лог. Описания инструментов и скил короткие: они оплачиваются токенами в каждой сессии старшего.

## Версионирование, отладка, тестирование

Плагины, хаб, Pi и старшие агенты обновляются независимо, поэтому совместимость проверяется явно.

- **Рукопожатие:** shim и хаб обмениваются версией протокола; при несовместимости понятная ошибка «обновите плагин» или «обновите хаб».
- **Версия Pi закреплена** в конфиге хаба: формат RPC может меняться. Обновление Pi только после прогона тестов адаптера.
- **Миграции базы** через `schema_version` с первого дня.
- **Сквозной идентификатор:** `task_id` и id старшей сессии во всех логах shim, хаба, хуков и Pi.
- **`/workers doctor`** проверяет цепочку: клиент, хук, shim, хаб, Pi, ключ провайдера, git, сеть.
- **Фейковый воркер** с заранее заданными сценариями (успех, вопрос, падение, зависание, нарушение протокола) для тестов без трат на модели.
- **Тесты по слоям:** модульные для роутера, учёта и статусов; интеграционные с фейковым воркером; редкие сквозные на настоящем Pi и дешёвой модели перед релизом.
- **Набор эталонных задач** (5 до 10) для сравнения моделей и проверки регрессий после обновлений.

## Правила репозитория

Автор идеи и проекта указан в шапке документа. ИИ-инструменты, применяемые в разработке, авторами и соавторами не являются.

- В коммитах, PR, issue, документации, комментариях в коде и релизах нет строк `Co-authored-by`, подписей вроде «Generated with …» и любых других указаний на соавторство ИИ.
- Правило записано в AGENTS.md репозитория, чтобы его соблюдали агенты, работающие с кодом. Проект использует только AGENTS.md как файл инструкций для агентов.
- Автоматические подписи агентов в коммитах и PR отключены в настройках каждого клиента.
- CI отклоняет коммиты и PR, в тексте которых есть `Co-authored-by` с адресом ИИ-сервиса или подпись генерации.
- Воркеры pi-hub коммитят от имени настроенного пользователя git и тоже без подписей моделей; модель и id задачи фиксируются только в базе хаба.
