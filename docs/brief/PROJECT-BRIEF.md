# Project Brief: pi-hub

**Дата:** 2026-11-26 | **Статус:** 📝 Черновик | **Версия:** 0.1 | **Автор:** @Fatima

> Спутники: [решения](decisions.md) · [открытые вопросы](open-questions.md) · [исследование](research.md) · [журнал](interview-log.md)
> Полная спецификация: [../spec/pi-hub-spec.md](../spec/pi-hub-spec.md) — бриф её сжимает и не заменяет.

## 1. Кратко

pi-hub — демон, через который старший агент (Codex, Claude Code, любой MCP-клиент) поручает работу младшим агентам Pi на дешёвых моделях (DeepSeek, GLM, Kimi, локальные). Старший планирует и принимает результат, младшие пишут код в изолированных ветках. Старший получает короткую сводку вместо полного хода работы, поэтому дорогие токены тратятся только на проектирование и приёмку.

## 2. Проблема

Дорогая модель старшего тратит большую часть токенов на исполнение: чтение файлов, правки, прогоны тестов. Дешёвые модели справляются с исполнением, но без постановки и приёмки дают низкое качество, а запускать их вручную и следить за ними неудобно.

## 3. Решение

Хаб принимает задачу от старшего через 8 MCP-инструментов, выбирает модель по роли, запускает Pi в отдельном worktree, доставляет вопросы воркера старшему, проверяет результат (тесты, линтер, типы) и возвращает конверт со сводкой, списком файлов и стоимостью.

## 4. Отличия

- Тонкие плагины без логики; одно ядро для всех клиентов.
- Режим делегирования выключен по умолчанию, и запрет держит хаб, а не промпт.
- Учёт токенов и стоимости по каждому шагу, бюджеты и квоты.
- Не «компания агентов»: главным остаётся старший агент пользователя.

## 5. Пользователи

Разработчик, который работает в Claude Code или Codex на дорогой модели и хочет снизить расход, не теряя контроля над качеством. Опционально — сборочная машина рядом с кэшами и тестовыми базами.

**Не входит:** собственный агент или модель, собственный шлюз к провайдерам, песочница уровня ОС, автономные «компании агентов».

## 7. Принципы

1. Логика только в хабе; плагины, shim и хуки тонкие и без ключей.
2. Запрет делегирования держит хаб; по умолчанию `off`.
3. Токены старшего дороги: короткие описания инструментов, конверт вместо журнала.
4. Хуки никогда не блокируют старшего при сбое (< 100 мс, ошибка → пропуск).
5. Ключи провайдеров только в `.env` машины хаба; хаб не слушает открытый интернет.
6. ИИ не указывается автором или соавтором нигде в репозитории.

## 8. Архитектура

**Тип системы:** локальный/удалённый демон + CLI + тонкие плагины клиентов.

| Слой                | Технология                              | Почему                                 |
| ------------------- | --------------------------------------- | -------------------------------------- |
| Ядро                | TypeScript, Node.js ≥ 24                | Язык Pi и MCP SDK                      |
| Протокол со старшим | MCP (stdio через shim, Streamable HTTP) | Поддерживают все клиенты               |
| Исполнитель         | Pi `--mode rpc`                         | Изоляция процессом, события с токенами |
| Хранилище           | SQLite (`node:sqlite`, WAL) + JSONL     | Один писатель, без сервера БД          |

Подробно: [overview](../architecture/overview.md), [stack](../architecture/stack.md), [ADR](../adr/).

## 9. Этапы

> Утверждено автором 2026-11-26 (OQ-14, BD-019). Исходная схема спецификации («5 этапов, 4 ворот») была встроенным объектом и в файл не попала; этапы восстановлены с учётом закрытых открытых вопросов. Каждый следующий этап начинается только после прохождения ворот предыдущего.

| Этап | Содержание | Ворота для перехода |
|---|---|---|
| 1. Ядро на одной машине ✅ (2026-11-27) | protocol, хранилище и миграции, менеджер сессий, запуск Pi по ADR-0011, worktree, `start/wait/status/result/cancel`, shim по unix-сокету, fake-worker, плагин Claude Code с `/architect`, `pi-hub init` с роутером «выкл» | Реальная задача проходит от `start` до слияния; интеграционные тесты на fake-worker зелёные |
| 2. Вопросы и качество ✅ (2026-11-27) | `ask` через Extension UI, `send`, `clarify`, подвал ответов, хук Stop, проверка качества, строка стоимости с пометкой неизвестной цены (без бюджетов и импорта цен — BD-021, BD-023) | Вопрос доходит старшему всеми тремя путями (BD-022) |
| 3. Роутинг и Codex | таблица ролей, эскалация, умный роутер в `pi-hub init` (пресеты, TypeSafe по умолчанию), профиль Codex со статическим списком инструментов, `usage_report`, `doctor` | На эталонных задачах доля PASS с первого раза измерена по 2+ моделям |
| 4. Многосессионность и удалёнка | владение, сироты, adopt, квоты, блокировка сборки, ssh-stdio, HTTP с токенами | Две сессии разных клиентов работают параллельно без пересечений; хаб на build-box |
| 5. Аналитика и панель | метрики, недельные предложения по таблице ролей, «липкая» смена модели, веб-панель | — |

Даты не заданы: старт назначает автор.

## 10. Риски

| Риск                                      | Мера                                                                   |
| ----------------------------------------- | ---------------------------------------------------------------------- |
| Формат RPC Pi меняется                    | Версия закреплена, контрактные тесты адаптера                          |
| Таймауты вызовов инструментов у клиентов  | `wait` с потолком (ADR-0006)                                           |
| Дешёвая модель нарушает протокол вопросов | Отмена и перезапуск с историей; метрика нарушений по моделям           |
| Воркер выполняет опасные команды          | Изоляция окружения (пользователь ОС, контейнер, ВМ); хаб лишь страхует |
| Клиенты не видят файл инструкций | Используется `AGENTS.md`, который оба клиента читают нативно; `CLAUDE.md` не создаётся (BD-012) |
